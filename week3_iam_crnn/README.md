# 第3周 · IAM 单词级手写文字识别(CRNN + CTC)

## 目标
进入真正的 HTR 任务:从图像直接识别出**不定长的单词文本**,
掌握 CRNN 结构与 CTC Loss 的对齐原理。

整体流程(任务书要求理解的主线):
```
Image -> CNN -> Feature Sequence -> BiLSTM -> CTC Decoder -> Text
```

## 数据集:IAM Handwriting Database

- 来源:官方 IAM(FKI, Bern),单词级 `words.tgz` + 标签 `ascii.tgz`
- 规模:**115,320 张单词图像**,其中切分正确的(`ok`)**96,456 条**
- 划分:采用学术界通用的 **Aachen 划分**(来自 OpenSLR 56)
  - train **47,999** / validation **7,559** / test **20,310**
  - 与文献常引用的 47,952 / 7,558 / 20,306 基本一致,结果可直接与论文对比
- 图像:灰度、白底黑字、尺寸可变(按「写手/表单」分层存放)

### 数据布局(解压后为平铺结构)

```
data/IAM/
├── a01/a01-000u/a01-000u-00-00.png     # 单词图像
├── a02/ ... l07/
├── words.txt                            # 标签(每行一个单词)
└── splits/{train,validation,test}.uttlist   # 按「表单」划分
```

`words.txt` 每行 9 个字段:
```
单词ID  状态  灰度  x y w h  词性  转写文本
a01-000u-00-00 ok 154 408 768 27 51 AT A
```

### 两个踩过的坑

1. **图像是转置存储的?不,是 IAM 的另一个坑:损坏文件。**
   IAM 压缩包内有极少量 **0 字节的空 PNG**(如 `a01-117-05-02.png`),
   直接 `Image.open` 会抛 `UnidentifiedImageError` 并**中断整个训练**。
   本项目在 Dataset 的 `__getitem__` 中加了容错顺延,并对 0 字节文件预先过滤。
2. **划分是按「表单」而非按「单词」。** `.uttlist` 里是表单 ID(如 `a01-000u`),
   需要把单词 ID 映射到所属表单(`a01-000u-00-00` → `a01-000u`)再判断归属。
   注意表单 ID 长度不固定(`a01-000u` 与 `a01-003`),不能按固定长度截取。

## 模型结构细节

```
输入 [N, 1, 32, 192]                          # 等比缩放到高32,定宽192补白边
  ↓ CNN(宽度方向共下采样 4 倍,得到 T=48 个时间步)
  Conv(1→64)   + BN + ReLU + MaxPool(2,2)     # 32×192 → 16×96
  Conv(64→128) + BN + ReLU + MaxPool(2,2)     # 16×96  → 8×48
  Conv(128→256)+ BN + ReLU
  Conv(256→256)+ BN + ReLU + MaxPool((2,1))   # 8×48   → 4×48
  Conv(256→256)+ BN + ReLU + MaxPool((2,1))   # 4×48   → 2×48
  ↓ 特征序列化:[N,256,2,48] → [48, N, 512](每个时间步 512 维)
  ↓ BiLSTM(512 → 256,2 层,双向)
  ↓ Linear(512 → 词表大小)
输出 [48, N, C] 的逐时间步 logits
```

**关键设计**:CNN 只在**高度方向**做两次额外池化,宽度方向只下采样 4 倍——
这样每个时间步对应图像的一小段水平区域,序列信息得以保留。

## 关键概念:CTC Loss 解决什么问题

传统分类要求「输入与标签一一对应」,但手写识别里**图像宽度与字符数没有固定比例关系**:
同一个 "hello" 可能写得又宽又窄。CTC 的做法是:

1. 允许模型在每个时间步输出一个字符**或 blank**(空白符);
2. 定义一套「多对一」映射:例如 `h h - e l - l o -` 与 `h - e e l l - o` 都能折叠成 `hello`
   (规则:先合并连续重复,再删除 blank);
3. 训练目标 = 让**所有能折叠成正确文本的路径**的概率之和最大。

这样模型自己学会「在哪里输出、在哪里空着」,无需人工标注每个字符的位置。

本项目用 `torch.nn.CTCLoss(blank=0, zero_infinity=True)`,
解码用**贪心策略**(每步取最大概率,再合并重复、去 blank)。

## 训练要点

- 优化器 Adam,学习率 1e-3,`ReduceLROnPlateau` 按验证 CER 衰减
- **梯度裁剪**(`clip_grad_norm_`, max_norm=5.0):CTC + RNN 组合容易梯度爆炸,这一步很关键
- 评价指标:**CER**(字符错误率)与 **WER**(单词错误率),均基于编辑距离
- 词表只从**训练集**构建,避免验证/测试集信息泄漏

## 训练过程观察(CTC 的典型现象)

训练初期 CER 会长时间停在 **100%**,这不是 bug:
CTC 需要先学会「输出 blank」,再逐渐学会「在正确位置输出字符」,
通常要若干个 epoch 后 CER 才会开始下降。因此**不能用前几轮的 CER 判断代码是否有问题**,
而应看**损失是否稳定下降**。

## 实验结果

训练 30 轮,共 61.6 分钟(RTX 3050),模型参数量 4,746,191。

| 指标 | 数值 |
|---|---|
| 测试集 CER(字符错误率) | **11.16%** |
| 测试集 WER(单词错误率) | **26.67%** |
| 完全识别正确 | **14,893 / 20,310(73.33%)** |
| 最优验证 CER | 8.12% |

CER 随训练轮次的变化:
```
66 → 34 → 21 → 17 → 14 → 13 → 11 → ... → 9 → 8 (验证集, %)
```
训练损失最终降至 0.0,而验证 CER 稳定在 8% 左右——模型对训练集**严重过拟合**,
但泛化能力已经达到可用水平。(文献中 CRNN 在 IAM 单词级的 CER 约 10%~15%,
本结果处于该区间内。)

## 数据增强对照实验

针对上面观察到的过拟合(train loss → 0.01,而验证 CER 停在 8%),又训练了一个
加数据增强的版本(轻量 `RandomAffine`:旋转 ±2°、平移 2%),其余设置完全一致。

| 指标 | 无增强 | 加增强 | 变化 |
|---|---|---|---|
| 最优验证 CER | 8.12% | **7.75%** | −0.37 |
| 测试集 CER | 11.16% | **11.05%** | −0.12 |
| 测试集 WER | 26.67% | 26.42% | −0.25 |
| 末轮训练损失 | 0.0105 | **0.1026** | 约 10 倍 |

**结论**:增强把训练损失从 0.01 拉高到 0.10(约 10 倍),说明它**确实抑制了过拟合**,
模型不再死记训练集;但测试 CER 只改善了 0.12 个百分点,**几乎没有实质提升**。

**这说明剩余误差的主要来源不是过拟合**,而是任务本身的固有难度:
1. **形近字母的天然歧义**(a/o、n/m、s/r),即使模型没「背题」也难以区分;
2. **写手差异**:Aachen 划分是按写手切分的,测试集的写手在训练时从未见过,
   验证集(7.75%)与测试集(11.05%)之间 3.3 个百分点的差距**在加了增强后依然存在**,
   印证了这是**跨写手泛化难度**而非过拟合。

这也解释了为什么单纯堆增强收益有限——**增强治的是过拟合,治不了任务本身的歧义性**。

## 失败案例分析

对 5,417 个错误样本做了统计归类:

### 1. 按错误类型分布

| 错误类型 | 占比 |
|---|---|
| 长度相同(字符替换/混淆) | 62.2% |
| 漏字(预测比真值短) | 23.6% |
| 多字(预测比真值长) | 14.2% |
| 仅大小写不同 | 3.5% |

### 2. 最常见字符混淆

| 真值 → 预测 | 次数 | 说明 |
|---|---|---|
| a → o | 179 | 差别仅在右侧一个小勾 |
| o → a | 166 | |
| t → l | 95 | 差别仅在横杠 |
| s → r | 95 | |
| u → n | 81 | |
| r → n | 80 | |
| n → m | 75 | m 比 n 多一竖 |

**规律:错误几乎全部发生在「字形相近、仅差一笔」的字母之间。**
这与第 1 周 MNIST 的发现高度一致(4→9、3→5、2↔7 也是形近数字混淆)——
说明**形近字符混淆是手写识别任务的共性难点**,与模型规模无关。

### 3. 典型失败样例

| 真值 | 预测 | 问题 |
|---|---|---|
| `Marie` | `Marse` | 形近字母 i→s |
| `changes` | `cronges` | a→o, h→n |
| `mid-way` | `midway` | 连字符被漏掉 |
| `CHRIS` | `ChR'sS` | **全大写词识别困难**,模型偏向输出小写 |
| `Stockton-on-Tees` | `Shoculon-on-Fees` | 长复合词 + 连字符,错误累积 |

**结论**:失败集中在三类——(1) 形近字母混淆;(2) 长词与含连字符/标点的词;
(3) 全大写等非典型大小写模式。这也指出了改进方向(见下)。

## 改进方向

- 加**语言模型**或 beam search 解码,利用词典约束纠正形近字错误;
- 针对形近字母(如 o/a、n/m)增大输入分辨率或加入更强的数据增强;
- 统一大小写或显式建模大小写,缓解全大写词的识别困难。

## 一个必须记下的工程坑:数据增强会拖垮 GPU 利用率

给训练集加数据增强后,训练**几乎停滞**:GPU 利用率只有 **3%**,显存却已分配 2GB。

**原因**:`DataLoader(num_workers=0)` 时,图像增强(PIL 的 `RandomAffine` 重采样)
在主进程里**串行**执行,GPU 每个 batch 都要等 CPU 处理完才能开工。
增强的 CPU 耗时超过了 GPU 的计算耗时,瓶颈完全落在 CPU 上。

**解决**:改用多进程加载 `--num-workers 4`,让增强在 4 个子进程里并行,
GPU 利用率立刻从 **3% 提升到 97%**,训练速度恢复正常。

```bash
python train.py --epochs 30 --augment --num-workers 4
```

**经验**:加了数据增强后如果发现训练变慢,先看 GPU 利用率——
若利用率很低但显存已占用,说明瓶颈在 CPU 端的数据预处理,应增加 `num_workers`。
